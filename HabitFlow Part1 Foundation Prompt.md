# HabitFlow — Часть 1 из 8: Фундамент и модель данных

## Контекст

Это первая из восьми последовательных частей разработки HabitFlow — трекера привычек (Go-бэкенд, React/TypeScript-фронтенд, PostgreSQL, деплой в K3s через Helm). К этому сообщению приложены конституция проекта (принципы и ограничения — следуй им во всём, что не оговорено ниже) и техническое задание (сущности, экраны, бизнес-требования; при расхождении с этим сообщением приоритет у ТЗ).

Дальнейшие части — только для ориентира, реализовывать не нужно:
2 — аутентификация и пользователи · 3 — доменная логика привычек · 4 — HTTP API · 5–6 — фронтенд · 7 — PWA/офлайн · 8 — деплой.

## Цель этой части

Заложить фундамент, на который будут опираться части 2–8: структура репозитория, минимальный CI, схема PostgreSQL с миграциями, core-сущности предметной области.

## Что нужно сделать

1. **Структура репозитория.** Layout, рассчитанный на будущие доменный слой, HTTP API, фронтенд и деплой-артефакты — без их кода, только директории/точки расширения там, где это оправданно. Кратко обоснуй выбор (монорепо vs полирепо, раскладка Go-модуля и т.д.).

2. **CI-скелет.** Пайплайн (GitHub Actions, если ТЗ не указывает иное) с шагами lint → build → test. Тестов пока нет, но шаг test должен быть настроен и корректно проходить на пустом наборе.

3. **Схема PostgreSQL и миграции.** Выбери и обоснуй инструмент миграций и способ доступа к БД — миграции должны запускаться из CLI отдельным шагом (пригодится для контейнеризации в части 8). Миграции — SQL, up/down, воспроизводимые. Индексы под предсказуемые паттерны выборки (по user_id, по датам).

   Core-сущности — отправная точка, уточняй по ТЗ:
   - **User** — учётная запись; в части 2 появится аутентификация и, возможно, связь родитель–ребёнок, если это есть в ТЗ — заложи в схему заранее.
   - **Habit** — привычка, привязанная к пользователю.
   - **Entry** — отметка о выполнении привычки за период.
   - **Streak** — проверь по ТЗ: отдельная таблица или производная величина от Entry. Если неочевидно — рассмотри оба варианта и выбери с обоснованием.

   Если ТЗ не даёт точных полей или ограничений для какой-то сущности — не придумывай их произвольно. Действуй по разделу конституции «Если информации недостаточно»: явно перечисли предположения и варианты, обоснуй выбор.

4. **Языковая конвенция.** Код, комментарии, имена таблиц/колонок, commit-сообщения — на английском, если ТЗ не указывает иное.

## Вне рамок этой части

Аутентификация, бизнес-логика (расчёт streak'ов и т.п.), HTTP-хендлеры, фронтенд, Helm-чарты, мониторинг. Если что-то из этого напрашивается по ходу — зафиксируй точку расширения (интерфейс, комментарий с указанием части), но не реализуй.
