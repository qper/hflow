# HabitFlow — Часть 2 из 8: Аутентификация и пользователи

## Контекст

Это вторая из восьми последовательных частей разработки HabitFlow (Go-бэкенд, React/TypeScript-фронтенд, PostgreSQL, K3s/Helm). К сообщению приложены конституция проекта, техническое задание и результат части 1 — структура репозитория, схема БД и миграции, а также блок «Контекст для части 2» из неё. Используй это как текущее состояние проекта, ничего не переделывай без необходимости.

Роадмап: 1 — фундамент (готово) · 2 — аутентификация (эта часть) · 3 — доменная логика привычек · 4 — HTTP API · 5–6 — фронтенд · 7 — PWA/офлайн · 8 — деплой.

## Цель этой части

Регистрация, вход, управление токенами и middleware авторизации поверх схемы из части 1. Эндпоинты этой части — рабочие, но минимальные: часть 4 переоформит их под общий контракт API (DTO, единый формат ошибок, OpenAPI). Не старайся сделать их окончательными.

## Что нужно сделать

1. **HTTP-фреймворк/роутер.** Выбери и обоснуй — часть 4 будет использовать этот же роутер для остальных хендлеров, без пересмотра.
2. **Хеширование паролей.** Выбери и обоснуй алгоритм — свежие рекомендации на сегодня, а не то, что было актуально на момент обучения модели.
3. **Регистрация.** Валидация email/пароля; если политика паролей не задана в ТЗ — предложи разумный дефолт и явно отметь как допущение.
4. **Вход и токены.** Определи стратегию (JWT vs серверные сессии, access+refresh или другое), срок жизни, механизм отзыва/ротации. Учти часть 7 — PWA с офлайн-режимом: клиенту нужно уметь распознать истёкший токен без постоянного соединения.
5. **Auth middleware.** Проверка токена, извлечение user_id в контекст запроса. Единственная точка, от которой будет зависеть часть 4, — держи интерфейс простым и стабильным.
6. **Модель родитель–ребёнок.** Проверь по ТЗ: если такая связь пользователей там описана — заложи её в схему (миграция поверх части 1) и в регистрацию/доступ. Если в ТЗ этого нет — не добавляй.
7. **Минимальные эндпоинты.** register, login, refresh, logout — достаточно для ручной проверки потока end-to-end. Без DTO-слоя и OpenAPI — это часть 4.
8. **Миграции.** Новые файлы поверх части 1: пароль-хэш, refresh-токены при серверном хранении, при необходимости — связь родитель–ребёнок.

## Вне рамок этой части

Единый API-слой с DTO/валидацией/форматом ошибок и OpenAPI (часть 4) — но выбранный роутер должен быть тем, на котором часть 4 продолжит строить. CRUD привычек и любая доменная логика (часть 3). Фронтенд, деплой.

## Формат ответа

- Дерево изменений/новых файлов и их содержимое.
- Обоснование: фреймворк, алгоритм хеширования, стратегия токенов.
- Список допущений, если ТЗ было неполным (особенно политика паролей и связь родитель–ребёнок).
- Блок **«Контекст для следующей части»** — финальная схема User (+связанные таблицы), способ получить user_id из контекста запроса, доступные middleware, полный список и формат эндпоинтов регистрации/входа/токенов. Сделай резюме самодостаточным (с учётом части 1), чтобы в части 3 не понадобился отдельно блок из части 1.
