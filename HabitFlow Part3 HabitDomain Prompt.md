# HabitFlow — Часть 3 из 8: Доменная логика привычек

## Контекст

Это третья из восьми последовательных частей разработки HabitFlow (Go-бэкенд, React/TypeScript-фронтенд, PostgreSQL, K3s/Helm). К сообщению приложены конституция проекта, техническое задание и результат части 2 — включая блок «Контекст для следующей части» из неё (он уже содержит нужное из части 1). Используй это как текущее состояние проекта.

Роадмап: 1 — фундамент (готово) · 2 — аутентификация (готово) · 3 — доменная логика привычек (эта часть) · 4 — HTTP API · 5–6 — фронтенд · 7 — PWA/офлайн · 8 — деплой.

## Цель этой части

Бизнес-логика привычек как чистый доменный слой, без единой зависимости от HTTP. Полностью покрывается юнит-тестами без поднятия HTTP-сервера. Часть 4 просто вызовет эти сервисы из хендлеров.

## Что нужно сделать

1. **Repository-интерфейсы.** Абстракции доступа к Habit/Entry(/Streak) в доменном пакете, конкретная реализация на Postgres — отдельно, тем же способом доступа к БД, что выбран в части 1. Сервисы зависят от интерфейса, а не от конкретной БД.
2. **CRUD привычек.** Создание/изменение/удаление/список привычек пользователя. Модель расписания (ежедневно / N раз в неделю / произвольные дни) — из ТЗ; если там не описано — предложи минимально достаточную модель и явно отметь как допущение.
3. **Логирование выполнения (Entry).** Идемпотентность повторной отметки за один период; определение границы «дня» для пользователя (часовой пояс) — не игнорируй этот момент, он напрямую влияет на корректность стриков.
4. **Расчёт стриков.** Текущий и максимальный стрик с учётом расписания привычки — пропуск не по расписанию (например, для «3 раза в неделю») не должен считаться разрывом. Это самая рискованная логика во всём проекте: заложи явные unit-тесты на смену часового пояса, редактирование расписания уже существующей привычки, пропуски, ретроактивную отметку задним числом (если она разрешена).
5. **Статистика/агрегаты.** Только если явно нужно по ТЗ — не добавляй сверх запрошенного.
6. **Юнит-тесты.** Обязательная часть результата, не опция — в первую очередь на расчёт стриков.

## Вне рамок этой части

Любой HTTP: ни одного хендлера, ни одного импорта транспортного слоя в доменном пакете — это часть 4. Аутентификация уже сделана в части 2, эта часть только принимает user_id как обычный параметр. Фронтенд, деплой.

## Формат ответа

- Дерево изменений/новых файлов и их содержимое.
- Обоснование: модель расписания, алгоритм расчёта стрика, способ хранения Streak (таблица или производная величина).
- Список допущений, если ТЗ было неполным.
- Явное покрытие тестами граничных случаев расчёта стриков.
- Блок **«Контекст для следующей части»** — сигнатуры сервисов/интерфейсов для вызова из хендлеров и точное поведение при ошибках (какие типы ошибок возвращаются, чтобы часть 4 могла смаппить их на HTTP-статусы). Сделай резюме самодостаточным, включая нужное из частей 1–2.
