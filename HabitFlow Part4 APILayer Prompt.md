# HabitFlow — Часть 4 из 8: API-слой

## Контекст

Это четвёртая из восьми последовательных частей разработки HabitFlow (Go-бэкенд, React/TypeScript-фронтенд, PostgreSQL, K3s/Helm). К сообщению приложены конституция проекта, техническое задание и результат части 3 — включая блок «Контекст для следующей части» из неё (он уже содержит нужное из частей 1–2). Используй это как текущее состояние проекта.

Роадмап: 1 — фундамент (готово) · 2 — аутентификация (готово) · 3 — доменная логика привычек (готово) · 4 — HTTP API (эта часть) · 5–6 — фронтенд · 7 — PWA/офлайн · 8 — деплой.

## Цель этой части

Единый, документированный и протестированный HTTP API поверх сервисов части 3 и авторизации части 2. Результат — контракт, на который будет опираться фронтенд (части 5–6), поэтому OpenAPI-спека здесь не формальность, а основной артефакт.

## Что нужно сделать

1. **Хендлеры для привычек/записей.** Полный CRUD и операции над Entry/статистикой поверх сервисов части 3 — эта часть только вызывает существующую логику, не добавляет новую.
2. **Переоформление auth-эндпоинтов.** Эндпоинты части 2 (register/login/refresh/logout) приводятся к единому контракту этой части — меняется только транспортный слой, не логика.
3. **DTO.** Request/response-структуры отдельно от доменных моделей и от структур БД — наружу не должны утекать внутренние поля.
4. **Валидация.** Единый подход по всем эндпоинтам; если нужна библиотека — обоснуй выбор по правилам конституции (не тащи зависимость ради нескольких строк).
5. **Единый формат ошибок.** Один механизм маппинга доменных/валидационных ошибок на HTTP-статусы и тело ответа, без дублирования в каждом хендлере.
6. **OpenAPI-спека.** Вручную или генерацией из аннотаций кода — обоснуй выбор. Это основной документ для части 5.
7. **Интеграционные тесты.** Против настоящего Postgres (обоснуй способ поднятия БД для тестов); покрыть минимум: полный цикл auth, CRUD привычки, отметку выполнения, один сценарий с ошибкой валидации и один с ошибкой авторизации.

## Вне рамок этой части

Новая бизнес-логика — этот слой только вызывает то, что сделано в частях 2–3; если обнаружится недостающая доменная функциональность, зафиксируй это как явный пробел, а не реализуй в обход слоя части 3. Фронтенд, PWA/офлайн, деплой.

## Формат ответа

- Дерево изменений/новых файлов и их содержимое, включая файл OpenAPI-спеки.
- Обоснование: библиотека валидации (если есть), формат ошибок, способ поддержки OpenAPI, способ интеграционного тестирования.
- Список допущений, если ТЗ было неполным.
- Блок **«Контекст для следующей части»** — базовый URL API, схема авторизации (где и как передаётся токен), путь к OpenAPI-спеке, список ключевых эндпоинтов. Сделай резюме самодостаточным, включая нужное из частей 1–3, — это то, что понадобится фронтенду для генерации клиента.
