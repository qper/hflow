# HabitFlow — Часть 5 из 8: Frontend — основа

## Контекст

Это пятая из восьми последовательных частей разработки HabitFlow (Go-бэкенд, React/TypeScript-фронтенд, PostgreSQL, K3s/Helm). К сообщению приложены конституция проекта, техническое задание и результат части 4 — включая блок «Контекст для следующей части» из неё (базовый URL API, схема авторизации, OpenAPI-спека, список эндпоинтов; он уже содержит нужное из частей 1–3). Используй OpenAPI-спеку части 4 как единственный источник правды о контракте — не описывай эндпоинты заново вручную.

Роадмап: 1–4 — бэкенд (готово) · 5 — frontend, основа (эта часть) · 6 — frontend, экраны привычек · 7 — PWA/офлайн · 8 — деплой.

## Цель этой части

Каркас фронтенда, который умеет аутентифицироваться против реального API из части 4 и типобезопасно его вызывать. Экранов привычек здесь ещё нет — это часть 6, но всё, от чего она будет зависеть (клиент API, роутинг, состояние, стайлинг), должно быть готово и обосновано здесь.

## Что нужно сделать

1. **Скелет проекта.** Vite + React + TypeScript, строгий tsconfig, lint/format — согласованно со стилем бэкенда из части 1.
2. **API-клиент из OpenAPI.** Выбери и обоснуй инструмент генерации типобезопасного клиента из спеки части 4; вшей регенерацию в процесс сборки/разработки, чтобы клиент не мог разойтись с контрактом.
3. **Роутинг.** Выбери и обоснуй роутер; раздели публичные маршруты (логин/регистрация) и защищённые — сейчас достаточно заглушки защищённой зоны, экраны наполнит часть 6.
4. **Состояние.** Выбери и обоснуй подход к серверному состоянию (кэш данных API) отдельно от локального UI-состояния; не тяни тяжёлую библиотеку, если задача решается проще (YAGNI).
5. **Хранение токена.** Это решение зависит от стратегии токенов из части 2 (JWT vs сессии) — выбери способ хранения на клиенте (localStorage, in-memory, httpOnly-cookie) и обоснуй выбор, учитывая компромисс между риском XSS и сложностью реализации, а не бери localStorage по умолчанию без рассмотрения альтернатив.
6. **Рефреш токена.** Автоматическое обновление при истечении (обёртка/интерцептор вокруг API-клиента), редирект на логин при неудаче.
7. **Базовый стайлинг.** Выбери и обоснуй подход (Tailwind, CSS-модули и т.д.); минимальная обвязка layout (шапка, навигация-плейсхолдер), которую часть 6 наполнит реальными экранами.
8. **Конфигурация окружения.** Base URL API через переменные окружения сборки — часть 8 будет прокидывать их через Helm/K8s, конкретный механизм сейчас не проектируй, просто не хардкодь URL.

## Вне рамок этой части

Экраны привычек, дашборд, чек-ин (часть 6). Service worker, офлайн, манифест PWA (часть 7). Контейнеризация и деплой (часть 8) — но собранный бандл должен быть обычным статическим выводом, без специфичных допущений о хостинге.

## Формат ответа

- Дерево проекта и содержимое всех файлов.
- Обоснование: инструмент генерации клиента, роутер, state-менеджмент, способ хранения токена, стайлинг.
- Список допущений, если ТЗ было неполным.
- Блок **«Контекст для следующей части»** — форма API-клиента и как им пользоваться, как проверить «залогинен ли пользователь» и получить текущего пользователя, структура маршрутов, стайлинг-конвенции. Сделай резюме самодостаточным, включая нужное из частей 1–4.
