# HabitFlow — Часть 6 из 8: Frontend — экраны привычек

## Контекст

Это шестая из восьми последовательных частей разработки HabitFlow (Go-бэкенд, React/TypeScript-фронтенд, PostgreSQL, K3s/Helm). К сообщению приложены конституция проекта, техническое задание и результат части 5 — включая блок «Контекст для следующей части» из неё (API-клиент, проверка авторизации, маршруты, стайлинг-конвенции; он уже содержит нужное из частей 1–4). Используй это как текущее состояние проекта.

Роадмап: 1–5 (готово) · 6 — frontend, экраны привычек (эта часть) · 7 — PWA/офлайн · 8 — деплой.

## Цель этой части

Экраны, которыми пользователь реально пользуется каждый день: список привычек, создание/редактирование, отметка выполнения, визуализация стриков. Это самая «продуктовая» часть проекта.

## Что нужно сделать

1. **Дашборд.** Список привычек пользователя, статус на сегодня (сделано/нет), текущий стрик — с первого взгляда.
2. **Создание/редактирование привычки.** Форма должна отражать ровно ту модель расписания, что определена в части 3 и отдана через DTO части 4 — не изобретай на клиенте отдельную модель расписания.
3. **Отметка выполнения (чек-ин).** Это самое частое действие в приложении — минимум кликов, оптимистичное обновление UI через слой состояния из части 5, чтобы не ждать ответа сервера визуально.
4. **Визуализация стриков/статистики.** Календарь-heatmap или аналог — ровно то, что фактически считает часть 3 через API части 4, не придумывай новые метрики на клиенте.
5. **Состояния загрузки/ошибки/пустого списка.** Для всех обращений к API — сеть недоступна, привычек ещё нет и т.д.
6. **E2E-тесты.** Выбери и обоснуй инструмент; минимум один сценарий: логин → создание привычки → чек-ин → обновление стрика.

## Вне рамок этой части

Офлайн-поведение и service worker (часть 7) — экраны проектируются в предположении, что сеть есть, но оптимистичные обновления из п. 3 не должны мешать части 7 добавить офлайн-очередь поверх того же слоя состояния. Контейнеризация и деплой (часть 8).

## Формат ответа

- Дерево проекта и содержимое всех файлов.
- Обоснование: подход к визуализации стриков, инструмент e2e-тестов.
- Список допущений, если ТЗ было неполным.
- Блок **«Контекст для следующей части»** — какие взаимодействия критичны для офлайн-режима (в первую очередь чек-ин), как устроен слой состояния и где в него встраиваться, актуальный список маршрутов. Сделай резюме самодостаточным, включая нужное из частей 1–5.
